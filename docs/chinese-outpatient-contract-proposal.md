# Предложение контракта китайской амбулаторной записи

Проверено 11 октября 2026. Это проект структуры SmartMed для обычного амбулаторного приёма, не реализованная версия API и не сертификат соответствия больничной системе. Конкретная больница/отделение пока не выбраны; их шаблон и интерфейс обмена потребуют отдельного сопоставления.

## Основания

1. [病历书写基本规范, 2010, статьи 11–14](https://www.nhc.gov.cn/bgt/s10696/201002/8cd7d4d70f4b42da839d2428dcbf723c.shtml): первичная амбулаторная запись включает время приёма, отделение, жалобы, историю текущего заболевания, анамнез, положительные и необходимые отрицательные признаки, результаты вспомогательных исследований, диагноз, лечебные рекомендации и подпись врача. Выделяются первичные и повторные записи.
2. [WS 445.2-2014, электронная амбулаторная/неотложная запись](https://www.nhc.gov.cn/wjw/s9497/201406/ca86202bf9ae46c0ad4b25d26d2f2375.shtml), [PDF](https://www.nhc.gov.cn/wjw/s9497/201406/ca86202bf9ae46c0ad4b25d26d2f2375/files/1739782369290_32523.pdf): ориентир для названий и сопоставления элементов данных. В опубликованном описании представлены аллергии, первичность обращения, жалобы, текущая и прошлая история, осмотр, исследования, предварительный диагноз и врачебные указания. Полное машинное сопоставление типов, длин и кодов пока не выполнено; этот проект не следует обозначать как реализацию всего стандарта.
3. [Правила 2024 года: 门（急）诊诊疗信息页](https://www.nhc.gov.cn/yzygj/c100068/202409/a58db40867bf4ea5a34f24a6b0486a9d.shtml), [официальное пояснение](https://www.nhc.gov.cn/yzygj/c100067/202409/0f2a60b7f8d44566bd84bac2e6b17e41.shtml): отдельная информационная сводка включает 72 пункта в четырёх категориях. Она не является самой амбулаторной медицинской записью. Пункт 10 продолжает ссылаться на правила написания медицинских записей. Для проекта важно отделить клинический черновик от отчётности.

Прямое открытие страниц NHC через web-инструмент возвращало 412; содержание получено из поисковой индексации официальных страниц. Это не подтверждает отсутствие более поздних изменений. При интеграции потребуется проверить применимые редакции и локальные требования больницы.

## Предлагаемая модель SmartMed: outpatient.v1

Названия ключей ниже — решение проекта; китайские подписи сопоставлены с опубликованными разделами. Это не официальный JSON NHC.

| Ключ | Подпись | Наполнение и источник |
|---|---|---|
| patient | 患者信息 | ID, имя, пол, дата рождения/возраст; ручной ввод или регистрационная система, модель не угадывает |
| encounter | 就诊信息 | ID приёма, отделение, время, outpatient, initial/follow_up/unknown; регистрация или врач |
| chief_complaint | 主诉 | Основная жалоба и продолжительность; из подтверждённого диалога |
| present_illness | 现病史 | Начало, развитие, сопутствующие симптомы, значимые отрицания, уже предпринятое лечение |
| past_history | 既往史 | Перенесённые болезни, операции и другие сообщённые сведения |
| allergy_history | 过敏史 | Статус истории аллергий; перечень веществ и реакций. Не ограничивать пенициллином |
| medication_history | 既往/现用药 | Фактически принимавшиеся лекарства; название, сообщённая доза, частота и сроки, без дополнения из справочника |
| physical_examination | 体格检查 | Фактические находки и измерения осмотра, сообщённые врачом или введённые вручную |
| investigations | 辅助检查 | Исследование, результат, дата/учреждение если известны; сообщённый пациентом результат помечается как patient_reported |
| assessment | 初步诊断 | Диагнозы/оценка, которые врач сформулировал; сохранить степень уверенности. Код выбирается/проверяется врачом |
| plan | 治疗处理意见 | Озвученные врачом исследования, лечение, назначения, рекомендации и повторный приём. Не смешивать с уже принятыми лекарствами |
| review | 医师审核 | ID врача, имя для документа, время подтверждения, версия и отметки проверки; создаёт сервер, не LLM |

Осмотр, исследования, диагноз и план допускают списки разной длины. Нулевой список означает отсутствие извлечённых элементов, но сам по себе не доказывает, что у пациента нет аллергий или заболеваний. Каждый раздел имеет отдельный статус полноты/неизвестности.

Для MVP предлагаем только обычный амбулаторный приём; расширения для традиционной китайской медицины и неотложной помощи оформлять отдельными профилями. Сведения регистрации и подпись показываются в документе, но не генерируются моделью.

## Факты, источник и проверка

Предложенная единица клинического содержания:

```json
{
  "id": "fact-1",
  "text": "咳嗽两天",
  "assertion": "present",
  "subject": "patient",
  "origin": "transcript",
  "reported_by": "patient",
  "evidence": [{"turn_id": 2, "quote": "我咳嗽两天了。"}],
  "review_state": "pending"
}
```

Это предложение нового формата, не тело работающего /v1/drafts. `assertion`: present/negated/unknown/uncertain. Неопределённый диагноз врача (например «可能») сохранять как uncertain, не переводить в подтверждённый. Не упомянутое поле — unknown. Противоречия хранить с исходными цитатами и флагом conflict, не выбирать сторону молча.

Идентификатор говорящего (speaker_id) и его медицинская роль (doctor/patient/third_party/unassigned) — отдельные свойства. Роли и расшифровка подтверждаются врачом до извлечения. Родственник может сообщать о пациенте: сохранить subject=patient, reported_by=third_party и цитату, затем требовать проверки; сведения о самом родственнике не переносить пациенту.

Для physical_examination/assessment/plan допустимы соответствующие утверждения врача, а вопрос, предположение о симптоме или обсуждение варианта лечения сами по себе не становятся находкой/назначением. Проверка роли и цитаты не доказывает правильного понимания смысла.

Для ручной правки допускается origin=manual со сведениями об авторе и времени. Не подделывать цитату для введённой вручную находки. Серверная запись аудита и версия меняются при сохранении; правка снимает подтверждение. Итоговая проверка включает текст, роли, каждый раздел, предупреждения и целиком текущую версию документа. Пустые обязательные разделы отмечаются для проверки, модель не заполняет их догадками.

## Изменения относительно текущей реализации

Сейчас prompt.py требует шесть полей и только цитаты пациента; модель получает Extraction JSON Schema, результат проверяется Pydantic и validate_extraction. Для нового документа потребуется одновременно обновить схему, инструкцию, разрешённые источники цитат, объединение длинных диалогов, API/хранение/версии, интерфейс и экспорт. Старые extraction.v2 сохранять читаемыми; неизвестные сведения при переносе не создавать.

Существующий schemas/soap.py пригоден как черновая заготовка типов, но автоматически переводить весь API на него нельзя: нужны происхождение фактов, статусы, ручные изменения, роли и регрессии.

## Первый реализуемый шаг

1. Подготовить синтетический китайский диалог, включающий несколько жалоб, анамнез, неизвестную аллергию, уже принятый препарат, находку осмотра, осторожную оценку врача и отдельно план.
2. Вручную зафиксировать ожидаемые разделы и ссылки на реплики; это учебный эталон, не клинический.
3. Реализовать версионированное извлечение outpatient.v1 на текстовых репликах и проверить настоящую Qwen, сохраняя extraction.v2.
4. Подключить редактирование разделов, проверку и печать/PDF той же сохранённой версии.
5. Добавить аудио и подтверждённые роли к уже работающему текстовому сценарию.

В PDF/печать выводить китайские клинические разделы и данные приёма/врача; исходный диалог и технические метаданные оставить отдельным приложением/JSON. Поля затрат, оплаты, документов личности и статистической отчётности не поручать извлечению из диалога.
