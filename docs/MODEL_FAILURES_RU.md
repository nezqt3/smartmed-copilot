# Почему Qwen3.5 давала 28/40 валидных ответов

Источник — сохранённые ответы первого сравнения:
`experiments/02_model_comparison/results/20261004T092905Z/qwen3.5_4b_quality.json`.
Это шесть полей на 40 синтетических диалогах, не полный SOAP и не клинический тест.

Всего 235/240 верных **статусов**, но 12/40 ответов нарушили правила нашего контракта.
У целого диалога один нарушенный пункт уже делал ответ невалидным. Это разные метрики.
Для полного вывода важны также значения, цитаты и принадлежность факта пациенту.

## 1. Пропущенная цитата при отрицании — нарушение формата

`test_01_negation`: пациент сказал `没有发烧，咳嗽两天。` —
«Температуры нет, кашляю два дня».

Модель верно определила отсутствие температуры, но ответила:

```json
{"status": "negated", "value": null, "evidence": []}
```

Правильно по нашему контракту:

```json
{"status": "negated", "value": null,
 "evidence": [{"turn_id": 2, "quote": "没有发烧"}]}
```

Смысл отрицания сохранился. Ошибка — отсутствие проверяемого основания.
Исправление: обязательная непустая цитата и повтор с сообщением об ошибке.

## 2. Длительность попала в поле кашля — ошибка значения

В том же диалоге:

```json
{"status": "present", "value": "两天",
 "evidence": [{"turn_id": 2, "quote": "咳嗽两天"}]}
```

Кашель действительно есть: **статус верный**. Но value «два дня» описывает длительность,
не симптом. Должно быть `咳嗽` в поле кашля и `两天` в поле длительности.

Старый валидатор это пропускал: «два дня» буквально содержится в цитате.
Новый добавляет узкую проверку признака кашля в value и уточняет инструкции.
Такая проверка не заменяет универсальную оценку соответствия значения полю.

## 3. «Не знаю» превратилось в «нет» — ошибка статуса

`test_16_family`: `我妈妈对青霉素过敏，我自己不知道。` —
«У моей мамы аллергия на пенициллин, про себя не знаю».

Ответ модели в поле аллергии:

```json
{"status": "negated", "value": null,
 "evidence": [{"turn_id": 1, "quote": "我自己不知道"}]}
```

Правильно: `unknown`, `value: null`, `evidence: []`.
Здесь модель **изменила смысл**: неопределённость стала отсутствием аллергии.
Старая проверка цитат это не ловила: слова пациента настоящие, но вывод неверный.

Новый валидатор разрешает отрицание аллергии только при явном отрицании пенициллиновой
аллергии в полной цитате. Недоказанное отрицание отклоняется и передаётся на повтор.
После неудачного повтора API возвращает ошибку, не подменяет ответ на unknown молча.
Словарь проверки узкий и требует отдельной проверки ложных отказов.

## 4. Цитата у неизвестного значения — только конфликт с нашим контрактом

`test_04_unknown`: пациент отвечает `我不清楚，从来没有检查过。` —
«Не знаю, никогда не проверял».

Модель верно поставила `unknown`, но приложила эту цитату. Наш контракт требует `[]`.
Это не выдуманный медицинский факт. Мы отклоняем такой ответ ради единообразия структуры.
Если захотим объяснять неизвестность цитатой, надо изменить схему и оценивание для всех
моделей одинаково, а не считать предыдущие результаты по новой шкале без оговорки.

## 5. Текст отрицания вместо null — нарушение формата

`test_12_doctor_only`: `我咳嗽，还没有吃药。` — «Кашляю, ещё не принимал лекарства».
У модели в поле принятых препаратов были `status: negated` и `value: "还没有吃药"`.
По смыслу отрицание верное, но текст должен находиться в цитате, а value быть `null`.
Это ловится структурной валидацией и исправляется повтором.

## Чего эти примеры не доказывают

Во время проверки нового API более полный пример из `examples/encounter_zh.json` выявил
ещё один отказ: модель превратила `200毫克` в `200 毫克` и так же изменила цитату.
Доза сохранилась по смыслу, но цитата уже не была буквальной. На первом повторе модель
исправила unknown с цитатой, а пробелы оставила, поэтому API вернул 502 и не сохранил
успешный черновик. Это ожидаемое поведение строгой проверки, но плохая удобность для пользователя.

В инструкции v3 уточнено сохранение символов и пробелов. Кроме того, ограничения
status/value/evidence перенесены в альтернативы самой JSON-схемы: для unknown возможен
только null и пустой evidence, для negated — null и непустой evidence, для present —
строка и непустой evidence. Успех отдельного примера после этих изменений не является
доказательством, что нормализация цитат больше никогда не повторится.

В итоговом варианте v6 добавлено ограничение цитат непосредственно при генерации:
сервер выделяет неизменяемые реплики/фрагменты пациента, а модель выбирает из перечисления
в JSON-схеме. У каждого варианта цитаты задан правильный turn_id. Сервер всё равно
проверяет полученный результат; value остаётся генерируемым текстом и проверяется отдельно.
Это ограничивает переписывание цитат, но не доказывает соответствие цитаты смыслу поля.

Промежуточные варианты v4/v5 показали именно такой риск: отсутствие температуры модель
использовала как основание отсутствия принятых препаратов. Цитата была настоящая, вывод —
необоснованный. Добавлен узкий контроль явного отрицания приёма лекарств, подобный
контролю отрицания пенициллиновой аллергии. Для всех остальных смысловых ошибок такой
универсальной защиты пока нет.

Нельзя достоверно вывести внутреннюю причину конкретной ошибки из одного ответа модели.
Наблюдаем смешение отрицания с неизвестностью, соседних полей и слабое соблюдение инструкции;
это не доказательство нехватки медицинских знаний или обязательной необходимости fine-tuning.
JSON-схема была включена уже в исходном сравнении: просто добавить ограничение JSON недостаточно.

Дальше нужно разделять три слоя:

1. Формат/контракт: схемы и детерминированная валидация.
2. Извлечение смысла: качество модели, инструкция, при необходимости обучение на размеченных парах.
3. Медицинская корректность полного документа: отдельная проверка специалистом.

Исправление инструкции на известных ошибках — разработка. Повтор этих же примеров показывает
регрессию, но для оценки общего прироста нужен новый удержанный набор, не участвовавший в настройке.
